# Tutorial 16: Remote Messaging
## Introduction
So far in these tutorials, all messages between objects have been sent using patch cords. Here we investigate another way to transfer messages between objects – by using the _remote messaging_ mechanism built into Max. There are specific objects for this called, [send](https://docs.cycling74.com/reference/send/ "send") and [receive](https://docs.cycling74.com/reference/receive/ "receive"), as well as methods for sending a [message](https://docs.cycling74.com/reference/message/ "message") box's contents to an object. Finally, we use some objects that allow the storage of variable data and can share values throughout complex patches.
As our designs get more complex, we need to take advantage of more techniques to modularize and compartmentalize our patches, making them easier to understand, maintain and extend. When our patches contain a lot of objects, long winding patch cord connections can cause unnecessary visual complexity. Using tools that allow message passing without patch cords can clean up our patches without changing how they operate.
## Playing with [send](https://docs.cycling74.com/reference/send/ "send") and [receive](https://docs.cycling74.com/reference/receive/ "receive")
`Technical note:` Many of the objects in the tutorial patch are colored to help you find related pairs of objects, but color has nothing to do with routing messages.
The most common way to send messages without patch cords is through the use of the [send](https://docs.cycling74.com/reference/send/ "send") and [receive](https://docs.cycling74.com/reference/receive/ "receive") objects. If we look at the tutorial patcher, the top left part of the patch shows a pairing of [send](https://docs.cycling74.com/reference/send/ "send") and [receive](https://docs.cycling74.com/reference/receive/ "receive") objects that pass an integer value. When we change the top [number](https://docs.cycling74.com/reference/number/ "number") box, the integer value is passed to the [send](https://docs.cycling74.com/reference/send/ "send")`fred` object. This value is “broadcast” throughout the Max environment, and can be “received” by any [receive](https://docs.cycling74.com/reference/receive/ "receive") object with the name `fred`. In this case, the [receive](https://docs.cycling74.com/reference/receive/ "receive")`fred` object immediately below gets the message, and outputs it to be displayed in the attached [number](https://docs.cycling74.com/reference/number/ "number") box.
Since a message is broadcast by _name,_ any [receive](https://docs.cycling74.com/reference/receive/ "receive") object sharing the [send](https://docs.cycling74.com/reference/send/ "send") object's `name` can receive the message. Hence, you can have more than one [receive](https://docs.cycling74.com/reference/receive/ "receive") object for a message, and more than one [send](https://docs.cycling74.com/reference/send/ "send") object sending messages using a single `name`. In our test patch, the [slider](https://docs.cycling74.com/reference/slider/ "slider") system connected to the [send](https://docs.cycling74.com/reference/send/ "send")`bob` object does just that – it sends the value (set with either the [slider](https://docs.cycling74.com/reference/slider/ "slider") or the [number](https://docs.cycling74.com/reference/number/ "number") box) to all [receive](https://docs.cycling74.com/reference/receive/ "receive") objects of `bob` messages. At the lower right of the patch are two different [receive](https://docs.cycling74.com/reference/receive/ "receive")`bob` objects: one connected to a [slider](https://docs.cycling74.com/reference/slider/ "slider") system, while another is connected directly to a [number](https://docs.cycling74.com/reference/number/ "number") box. Changing the top [slider](https://docs.cycling74.com/reference/slider/ "slider") value changes both of the receiving values simultaneously.
When working with pairs of [send](https://docs.cycling74.com/reference/send/ "send") and [receive](https://docs.cycling74.com/reference/receive/ "receive") objects, it’s important to realize that the message will be grabbed by any [receive](https://docs.cycling74.com/reference/receive/ "receive") object anywhere in the Max environment – even in another patcher. To test this, open a new patcher (selecting **New Patcher** from the **File** menu). Add a new object, and enter [receive](https://docs.cycling74.com/reference/receive/ "receive")`bob`. Connect the output of the [receive](https://docs.cycling74.com/reference/receive/ "receive") object to a [number](https://docs.cycling74.com/reference/number/ "number") box, then return to the tutorial patch. If you change our test [slider](https://docs.cycling74.com/reference/slider/ "slider"), you will see the output received in the new patch as well as all other [receive](https://docs.cycling74.com/reference/receive/ "receive")`bob` objects in the main patcher.
When working with other people’s patches, you may see objects named “s” or “r”. Since the [send](https://docs.cycling74.com/reference/send/ "send") and [receive](https://docs.cycling74.com/reference/receive/ "receive") objects are so popular, they have _alias_ (or shorthand) names of “s” and “r” respectively. In addition to being easier to type, these shortcut names also allow you to keep the object small!
## Working with `;` and [forward](https://docs.cycling74.com/reference/forward/ "forward")
Another common use of remote messaging is to send the contents of a [message](https://docs.cycling74.com/reference/message/ "message") box to one or more [receive](https://docs.cycling74.com/reference/receive/ "receive") objects. Rather than always having to connect [message](https://docs.cycling74.com/reference/message/ "message") boxes to [send](https://docs.cycling74.com/reference/send/ "send") objects, there is a special format of the [message](https://docs.cycling74.com/reference/message/ "message") box that can directly send messages to [receive](https://docs.cycling74.com/reference/receive/ "receive") objects. This involves placing a semicolon (`;`) and the `name` of a [receive](https://docs.cycling74.com/reference/receive/ "receive") object in front of the message. Thus, `; bob 155` is the equivalent of sending the value `155` to any [receive](https://docs.cycling74.com/reference/receive/ "receive") object named `bob`.
The large gold `message` box at the bottom-left of the patch is an example of direct message sending. Four messages are generated: two are sent to `lcd1` destinations, and two are sent to `lcd2` destinations. If you click on the [message](https://docs.cycling74.com/reference/message/ "message") box, you will see that the two [lcd](https://docs.cycling74.com/reference/lcd/ "lcd") objects each receive the appropriate draw commands through their respective [receive](https://docs.cycling74.com/reference/receive/ "receive") objects - the top [lcd](https://docs.cycling74.com/reference/lcd/ "lcd") (`lcd1`) draws a blue circle; the bottom [lcd](https://docs.cycling74.com/reference/lcd/ "lcd") (`lcd2`) draws a green rectangle.
Another common need we might have is to send messages to one of several destinations based on some logical criteria. This can be done using switching logic (e.g. the [gate](https://docs.cycling74.com/reference/gate/ "gate") object connected to different [send](https://docs.cycling74.com/reference/send/ "send") objects). However, we can also use the [forward](https://docs.cycling74.com/reference/forward/ "forward") object to route messages to selected locations. Just above our green [message](https://docs.cycling74.com/reference/message/ "message") box example is a [forward](https://docs.cycling74.com/reference/forward/ "forward") object with supporting logic.
You can select which named destination should receive the messages from [forward](https://docs.cycling74.com/reference/forward/ "forward") : the `send` message, sent to the [forward](https://docs.cycling74.com/reference/forward/ "forward") object, will set the destination name for any incoming messages. Once a destination has been set, all messages will be routed appropriately. If we click on the `send lcd1` message, changes to the [number](https://docs.cycling74.com/reference/number/ "number") box will cause a colored rectangle to be created in the first [lcd](https://docs.cycling74.com/reference/lcd/ "lcd") object. If we click on the `send lcd2` message, it changes the output destination of the [forward](https://docs.cycling74.com/reference/forward/ "forward") object to the [receive](https://docs.cycling74.com/reference/receive/ "receive")`lcd2` object. Now, any changes to the [number](https://docs.cycling74.com/reference/number/ "number") box will cause the creation of a rectangle in the second [lcd](https://docs.cycling74.com/reference/lcd/ "lcd") object.
By a similar token, a [receive](https://docs.cycling74.com/reference/receive/ "receive") object with _no_ arguments can be used to receive messages from any named [send](https://docs.cycling74.com/reference/send/ "send") or appropriately configured [forward](https://docs.cycling74.com/reference/forward/ "forward") or [message](https://docs.cycling74.com/reference/message/ "message") box. The `set` message to the [receive](https://docs.cycling74.com/reference/receive/ "receive") object allows it to "switch names", so to speak, so that it can listen to different parts of the patcher. Next to our [forward](https://docs.cycling74.com/reference/forward/ "forward") object is one such [receive](https://docs.cycling74.com/reference/receive/ "receive") object. By switching it between listening to `bob` and `fred` (using the [message](https://docs.cycling74.com/reference/message/ "message") boxes) and then manipulating the [number](https://docs.cycling74.com/reference/number/ "number") box and [slider](https://docs.cycling74.com/reference/slider/ "slider") object sending to those names, we can see how this works. Setting the [receive](https://docs.cycling74.com/reference/receive/ "receive") to a `name` that doesn't exist (e.g. `none`) will disconnect it from listening to anything in our patch. Note that in order for a [receive](https://docs.cycling74.com/reference/receive/ "receive") object to be "switchable", it needs to be created _without_ an argument (otherwise it has no inlet).
## The [int](https://docs.cycling74.com/reference/int/ "int"), [float](https://docs.cycling74.com/reference/float/ "float"), and [value](https://docs.cycling74.com/reference/value/ "value") objects
Sometimes, when working with patch programming, we need a place to stash a value until we need to use it. While we could use integer and floating-point [number](https://docs.cycling74.com/reference/number/ "number") boxes, those objects have the possibility of having the user change the value through their UI. In order to provide simple variable storage and recall, there are a set of objects specifically used for this purpose. The [int](https://docs.cycling74.com/reference/int/ "int") and [float](https://docs.cycling74.com/reference/float/ "float") objects can act as temporary storage of values; values coming in the _left_ inlet are stored and sent out the outlet immediately, while values coming in the _right_ inlet are stored without output. If you want to retrieve the value stored in an [int](https://docs.cycling74.com/reference/int/ "int") or [float](https://docs.cycling74.com/reference/float/ "float") object, you need to send a `bang` message (such as from a [button](https://docs.cycling74.com/reference/button/ "button") object) into the left inlet.
One of the advantages of the [int](https://docs.cycling74.com/reference/int/ "int") and [float](https://docs.cycling74.com/reference/float/ "float") objects is that you can initialize the value without using any other message. The argument provided with the object gives it an initial value; there is no need to set these up with [loadbang](https://docs.cycling74.com/reference/loadbang/ "loadbang") messages or other functions. If we look at the [int](https://docs.cycling74.com/reference/int/ "int") and [float](https://docs.cycling74.com/reference/float/ "float") objects to the right of our patch, we can see how they work. They do not send their value when the patch is loaded; sending a `bang` into them with the [button](https://docs.cycling74.com/reference/button/ "button") objects outputs their initialized value. Once we start entering numbers into them from the [number](https://docs.cycling74.com/reference/number/ "number") boxes, those new values are stored inside the objects until we `bang` them again.
In our patch, just below the [int](https://docs.cycling74.com/reference/int/ "int") and [float](https://docs.cycling74.com/reference/float/ "float") object, we find a pair of objects called [value](https://docs.cycling74.com/reference/value/ "value"). The [value](https://docs.cycling74.com/reference/value/ "value") object is like a combination of an [int](https://docs.cycling74.com/reference/int/ "int") / [float](https://docs.cycling74.com/reference/float/ "float") object and a [send](https://docs.cycling74.com/reference/send/ "send") / [receive](https://docs.cycling74.com/reference/receive/ "receive") pair – each of the [value](https://docs.cycling74.com/reference/value/ "value") objects has a `name` (in this case, `joe`), and any values placed in one of the objects is shared with all of the other [value](https://docs.cycling74.com/reference/value/ "value") objects with that `name`. One thing to notice is that sending a message into a [value](https://docs.cycling74.com/reference/value/ "value") object does not trigger output – you need to explicitly force output by sending a `bang` message to the object. In our test patch, change the value of one object then `bang` the other: you will see that the value is magically transferred from one to the other.
Unlike the [int](https://docs.cycling74.com/reference/int/ "int") and [float](https://docs.cycling74.com/reference/float/ "float") objects, the `value` object can take messages of _any_ type; symbols, integers and floats can all be stored by the [value](https://docs.cycling74.com/reference/value/ "value") object, as can a list. While this is convenient, it also means that you need to be careful about the objects that you connect to a [value](https://docs.cycling74.com/reference/value/ "value") object to display the output. Our test patch has [number](https://docs.cycling74.com/reference/number/ "number") boxes connected to the value objects; however, it might be better to connect a [message](https://docs.cycling74.com/reference/message/ "message") object (by the right inlet) or other display object that can accept a diverse set of values.
## Summary
Being able to send messages without having to connect patch cords can give us more flexibility in patch layout, and can also allow us to produce and route messages throughout very complex patches. The [send](https://docs.cycling74.com/reference/send/ "send") and [receive](https://docs.cycling74.com/reference/receive/ "receive") objects are the most common way of passing messages around a patch, but the use of `;` notation in [message](https://docs.cycling74.com/reference/message/ "message") boxes and the use of the [forward](https://docs.cycling74.com/reference/forward/ "forward") object for routing can help minimize the visual complexity of our work. Finally, we saw how values can be stored in the [int](https://docs.cycling74.com/reference/int/ "int") and [float](https://docs.cycling74.com/reference/float/ "float") objects, and how a [value](https://docs.cycling74.com/reference/value/ "value") object can be used to both store and forward data that is sent into it. All of these objects and techniques are important for working with complex patching systems.
